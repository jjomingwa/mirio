## 요청 배경

사용자는 첫 번째 번호 기반 플랜 작성을 요청했지만, 이번에 계획할 구현 설명을
“이번 요청에는 구현이 없다”라고 명시했다. 따라서 특정 기능, 결함 또는 사용자
동작을 추론해 계획하는 것은 요청 범위를 벗어난다.

이 문서는 구현할 기능이 아직 정의되지 않았다는 사실과, 실행 가능한 플랜으로
전환하려면 어떤 정보와 조사가 필요한지를 기록한다. 번호 플랜 체계 자체의 구축은
이번 문서 관리 작업이며 게임 기능 구현으로 간주하지 않는다.

## 목표

정의되지 않은 제품 요구사항을 임의로 발명하지 않고 현재 요청의 빈 범위를
명시한다. 향후 구체적인 구현 요청은 새 번호의 플랜으로 작성하며, 관련 코드,
완료 조건, 구현 순서와 검증 방법은 그 요청을 받은 뒤 조사해 확정한다.

## 사용자 관점 동작

이번 플랜으로 추가되거나 변경되는 게임 동작은 없다. 사용자는 현재 게임을 기존과
동일하게 이용한다.

## 현재 코드베이스 조사

### 관련 구조

현재 요청에는 기능 대상이 없으므로 아래 구조는 특정 구현과 관련됐다고 단정할 수
없다. 향후 요청의 조사 출발점을 확인하기 위해 저장소의 실제 경계만 기록한다.

- `src/App.tsx`: React 기반 타이틀, HUD, 설정, 터치 조작과 게임 이벤트 연결
- `src/game/scenes/`: Phaser 장면과 프레임 단위 게임 진행
- `src/game/data/`: 월드와 코스의 타입, 스키마, 데이터, 라우팅
- `src/game/state/`: Zustand UI 상태와 Zod 기반 로컬 저장
- `src/game/systems/`: 입력, 이동, 오디오, 코스 생성과 효과 수명 관리
- `tests/`: Vitest 단위·무결성 테스트와 Playwright 브라우저 흐름
- `.goal/`: 상업 목표, gate, backlog, evidence와 결정적 실행 규칙
- `docs/`: 아키텍처와 조사 기록. 조사 시점에는 기존 플랜 폴더가 없었다.

### 관련 파일

- `README.md`: 게임 경험, 실행 방법과 상위 디렉터리 책임을 설명한다.
- `docs/ARCHITECTURE.md`: React와 Phaser의 경계, 저장·월드 그래프 계약과 완료
  증거를 정의한다.
- `docs/RESEARCH.md`: Phaser, React, Howler, Zod, Zustand, Vite, Vitest와
  Playwright의 책임을 기록한다.
- `src/App.tsx`: 저빈도 UI 상태를 표시하고 `gameEvents`로 Phaser와 통신한다.
- `src/game/events.ts`: UI와 게임 장면 사이의 typed event 이름을 정의한다.
- `src/game/state/store.ts`: UI mode, HUD와 save 변경 동작을 소유한다.
- `src/game/state/save.ts`: `localStorage` 저장, Zod 검증, 정규화와 진행 상태 변경을
  담당한다.
- `tests/e2e/smoke.spec.ts`: 실제 브라우저의 오프닝, 월드맵, 코스 흐름을 검증한다.
- `package.json`: format, lint, unit, build, e2e와 Goal Harness 검증 명령을
  제공한다.

위 파일들은 저장소 구조 조사 근거이며, 아직 정의되지 않은 기능의 수정 대상은
아니다.

### 기존 동작

`README.md`와 확인한 코드에 따르면 React UI가 Phaser 게임을 감싸고,
`gameEvents`가 양쪽 경계를 연결한다. 진행과 설정은 Zustand store를 거쳐
`localStorage`에 저장되며 Zod로 정규화된다. 특정 구현 요청이 없으므로 이 동작 중
무엇을 변경해야 하는지는 확인할 수 없다.

### 재사용 가능한 요소

후속 요청의 성격에 따라 기존 event bus, Zustand store, Zod 스키마, Phaser scene,
Vitest와 Playwright 검증 구조를 재사용할 가능성이 있다. 현재는 관련성이 확정되지
않았으므로 재사용 대상으로 지정하지 않는다.

### 확인된 제약

- `AGENTS.md`는 `.goal/backlog.json`을 유일한 자율 작업 큐로 지정한다.
- Goal Harness에는 이미 활성 항목 `Q-010-SIGNATURE-HOOK-PROTOTYPE`가 있으므로 다른
  backlog item을 동시에 활성화할 수 없다.
- 저장소는 조사 시점에 기존 사용자 변경이 있는 dirty worktree다. 후속 구현은
  사용자 변경을 보존하고 겹치는 파일을 편집하기 전에 차이를 확인해야 한다.
- 스토어, 운영체제, audience와 attribution 관련 전역 결정은 아직 확정되지 않았지만
  후속 구현이 해당 경계에 의존할 때만 직접 blocker가 된다.
- `NOTE.md`는 개발자의 비공개 메모이므로 조사하지 않았다.

### 1. 구체적인 후속 요청 확정

- 작업 내용: 구현 목적, 사용자 관점 동작, 포함·제외 범위와 검증 가능한 완료
  조건을 사용자 요청에서 확인한다.
- 수정 예상 파일: 없음
- 의존 관계: 사용자의 구체적인 구현 요청
- 완료 판단 기준: 제품 동작을 추측하지 않고 최소 한 개 이상의 검증 가능한 완료
  조건을 작성할 수 있다.
- 검증 방법: 사용자 요청과 작성된 목표·범위를 항목별로 대조한다.

### 2. 요청 관련 코드와 계약 조사

- 작업 내용: 1단계에서 확정된 동작에 직접 연결된 코드, 상태, 데이터, 테스트,
  설정과 상위 문서를 읽는다.
- 수정 예상 파일: 없음
- 의존 관계: 1단계
- 완료 판단 기준: 확인한 사실, 가정, 제약과 예상 수정 파일을 구분해 설명할 수
  있다.
- 검증 방법: 경로별 책임을 실제 심벌과 테스트에 대조하고 조사하지 않은 영역은
  미확정으로 남긴다.

### 3. 별도 번호의 실행 가능한 플랜 작성

- 작업 내용: `PLAN-001`부터 사용 가능한 다음 번호로 구현 순서, 단계별 완료 기준,
  위험과 검증 방법을 작성하고 인덱스를 갱신한다.
- 수정 예상 파일: `docs/plans/README.md`,
  `docs/plans/PLAN-NNN-<slug>.md`
- 의존 관계: 1~2단계
- 완료 판단 기준: 새 플랜이 `docs/plans/README.md`의 `Ready` 기준을 만족하거나
  남은 blocker를 명시한 `Draft`로 기록된다.
- 검증 방법: 템플릿 구조, 링크, 번호 중복, 요청 추적성과 검증 가능성을 확인한다.
